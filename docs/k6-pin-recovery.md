# PIN ownership recovery

An unreadable PIN is an existing lock, not an invitation to create a first PIN. The PIN screen checks effective health before accepting input or a normal biometric callback. Genuine onboarding can create a PIN only when no PIN exists. An unreadable record offers a previously enabled strong biometric check, a matching wallet backup, and (where the device has a secure lock) a separate device-credential path for public viewing.

A recovery grant lives only in memory for ten minutes, measured by Android elapsed realtime. Its random challenge may be passed with a public wallet ID and key scope to the backup input screen. The grant itself, its authorization, entered backup, and PIN confirmation are never saved in navigation state. The ordinary import/rebind shortcut cannot authorize a PIN reset. A real backup must pass K4 verification against a durable wallet identity; that identity is read again before reset. A matching backup may repair that key before the PIN is changed, as disclosed on the screen. Other keys remain unavailable for signing during a view-only session.

The grant binds the exact typed PIN record. Reset rechecks effective unreadable health and compares the original snapshot immediately before the durable replacement. A concurrently changed PIN, a now-readable original PIN, expired/replaced/canceled proof, or changed public identity rejects the reset. The old value is retained exactly, including a malformed integer, long, boolean, float, or string set. The new PIN is encrypted and read back before health is published. An ambiguous persistence failure keeps the existing restart-required storage latch.

The strong recovery prompt requests only `BIOMETRIC_STRONG` and accepts a biometric result only. The device-credential prompt accepts a credential result only (API 30+), with the platform keyguard confirmation activity on earlier versions. Normal biometric unlock still rechecks readable PIN health and prior biometric enablement. A ViewModel-owned prompt gate keeps a canceled prompt as the owner of its callback until its terminal result arrives; a late ordinary unlock result cannot be relabeled as a new strong recovery check after pause or fragment recreation.

Device-credential success cancels the recovery grant and opens Main directly, discarding any pending send, export, or dapp destination. The process-local view-only flag blocks central signing/key-export reads and the signing-availability APIs. Public identity/status reads remain available. A banner routes back to PIN recovery. Successful wallet authentication or completed reset clears the flag; process death discards it and requires authentication again. This path does not bypass startup database or master-key safety gates.

The PIN screen and backup input use screenshot protection and exclude view state, autofill, and personalized keyboard learning. Temporary PIN confirmation is cleared when the screen stops, and backup input/job cleanup is inherited from the qualified K5 flow. Input or private values are absent from diagnostic `toString` output. Actions scroll at large text sizes, with separate wording for ownership proof and device-authenticated public viewing in all eight shipped locales.
