# Kaia history provider production gate — 2026-09-24

Android retains chain IDs `8217` (mainnet) and `1001` (Kairos), every existing asset ID, precision, wallet identity and signing path. The bundled history configuration now uses KaiaScan OAPI for both chains; `KLAYTN` remains the serialized history type for compatibility with stored and remote chain records. The exact retired `https://scope.klaytn.com/api/v1` and `https://scope.kaia.io/api/v1` mainnet URLs are accepted only as migration sources and rewritten to the mainnet KaiaScan host before the Bearer key is attached. Unknown hosts, ports, URL credentials, query strings, cross-chain hosts and unrecognized chain IDs fail before a request.

The [native account transactions](https://docs.kaiascan.io/api/Account/Transaction/get-account-transactions) contract is `GET /api/v1/accounts/{address}/transactions?page=&size=`. Its rows contain decimal-unit `amount` and `transaction_fee`, a terminal `Success`/`Fail` status and `datetime`; `paging.current_page`, `paging.total_page`, `paging.total_count` and `paging.last` govern the cursor. The separate [fungible-token transfer](https://docs.kaiascan.io/api/Account/Transfer/get-token-transfers) contract is `GET /api/v1/accounts/{address}/token-transfers?contractAddress=&page=&size=`. It returns `contract.contract_address`, block ID and decimal-unit `amount`, but no fee or terminal receipt status. Android converts each decimal to smallest units exactly, rejects excess precision or 256-bit overflow, binds token rows to the requested contract and queried account, and leaves token fee unknown. An indexed token-transfer row is mapped as a completed *token movement* because it is attached to a block; this is an inference, not a documented successful transaction receipt, and must be reconciled with funded receipts before release. Fee-payer-only rows are not presented as incoming transfers. Unrepresentable nonterminal pages fail visibly instead of advancing a local cursor. The [Kaia Foundation's API guide](https://blog.kaia.io/how-to-access-kaiachain-data-using-kaiascan-api/) specifies the `Authorization: Bearer <key>` header; `FL_ANDROID_KAIASCAN_API_KEY` supplies the key. The free plan's 500-row limit is respected despite the endpoint schema's 2,000-row maximum.

This is a source candidate, not live provider acceptance. A real operator-controlled KaiaScan key has not been provisioned for this checkout. A keyless public probe returns HTTP 401, which only establishes that unauthenticated traffic is rejected. Before production distribution, the operator must run native successful/failed and fee-delegated transactions plus token transfers on mainnet and Kairos, compare displayed amount/fee/status against independent on-chain receipts, exercise several pages and fresh indexing, verify 401/429/outage behavior and the wallet's retry/explorer path, and repeat on the exact final signed artifacts. The token endpoint lacks receipt status and fee, so terminal token status and fee display must be independently qualified against the deployed chain or represented as unknown in the final UX. API keys, funded wallets and final store-delivered builds are not available in this source review.
