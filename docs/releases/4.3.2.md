## Why

On 7 November 2026 a review of 4.3.1 (233) found ways keys could be exposed: biometric unlock was a UI gate
only, a re-locked wallet still signed dApp requests, the PIN was not part of the encryption, and several
screens and copies leaked secrets. The owner asked to fix all of them and to ship no closed-source library.

### What users notice

- Biometric unlock may turn off once after updating (and after any biometric change) until the next PIN entry
  offers it again; on phones with only weak (Class 2) biometrics the wallet unlocks with the PIN.
- Exports, recovery screens, PIN changes and Drive backups ask for the PIN.
- A PIN check takes about a quarter to one second longer (Argon2id).
- dApp requests that arrive while the wallet is locked appear after the PIN.
- Google Drive needs one new sign-in, in the browser.
- New backup passwords must be strong; older backups open as before.

### Upgrade safety

- Keys and derivations are byte-identical: the source-built sr25519 library against the 4.3.1 library on
  20,000 random seeds and 5,000 derivation paths; BouncyCastle against recorded EdDSA-Java, SpongyCastle and
  polkaj outputs; the in-repo TON code against ton-kotlin; JSON backups from Android, iOS and the web wallet.
- The PIN envelope seals existing wallets one key at a time after the first PIN entry, with compare-and-set
  and verified read-back; an interrupted migration resumes without loss; no pass that runs before the PIN
  moves or rewrites a sealed value; emergency export still reveals every secret with the PIN.
- WalletConnect sessions made with 4.3.1 are imported and the old SDK's files are deleted only after a
  verified import (emulator: a real 4.3.1 install upgraded in place, its session used afterwards).
