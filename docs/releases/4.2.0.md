# Fearless Android 4.2.0 migration-safe Open Testing candidate

## Candidate identity and purpose

- Package: `jp.co.soramitsu.fearless`
- Version name: `4.2.0`
- Version code: `230`
- Immutable release tag: `v4.2.0+android.230`
- Initial destination: the existing `beta`/Open Testing track, not Production

Google Play Production is currently version code 229. Build 230 is reserved for
the first migration-safe 4.2.0 testing candidate and must remain immutable. Its
primary release requirement is that an upgrade never deletes or silently
replaces a user's wallet data when Room, encrypted preferences, Android
Keystore, or a cross-store mutation is inconsistent.

### Observed production startup crash

An authenticated Play Console snapshot reviewed on 2026-07-30 for production
version code 229 (`4.2.0`) showed one startup crash group affecting five users
in five events. The stack enters `BaseActivity.onCreate` through
`NavHostFragment.onCreate` and `FragmentManager.restoreSaveStateInternal`, then
fails in `Fragment.instantiate` with `NoSuchMethodException` while Android is
handling an Activity relaunch. This is stale/non-restorable FragmentManager
state, not a Room migration exception.

Build 230 addresses that exact lifecycle path before database startup:

- the launcher and legacy task entry use the lightweight `WalletGateActivity`,
  which deliberately calls `super.onCreate(null)` so Android cannot instantiate
  fragments saved by an incompatible prior navigation graph;
- only the primitive startup payload sequence is recovered from the incoming
  Activity bundle, while the newest launcher/deep-link intent remains owned by
  the process startup session;
- `ErrorDialog`, `InfoDialog`, and `SecurityWarningBottomSheet` expose public
  empty constructors for ordinary FragmentManager restoration; and
- `WalletGateActivityLifecycleTest.legacyGateRelaunchDiscardsNonRestorableFragmentState`
  installs a deliberately non-restorable fragment and recreates the Activity,
  proving the obsolete fragment state is discarded instead of crashing.

The Fragment fix does not replace migration qualification. Exact released Room
schemas, non-empty wallet state, secure-storage failures, and in-place Play
upgrades remain separate mandatory gates below.

### WalletConnect initialization failure containment

A release-like Internal App Sharing build exposed a delayed cold-start crash
when Reown initialization was unavailable: first access to `WCDelegate`
registered both SDK delegates from the Kotlin object initializer, so
`CoreClient.setDelegate` raised an `IllegalStateException` that became an
`ExceptionInInitializerError` on the main thread.

Build 230 now keeps that optional integration outside the startup failure
boundary:

- delegate registration starts only from `WalletKit.initialize(onSuccess)` and
  is synchronized, idempotent, and safe to retry after partial initialization;
- loading or observing `WCDelegate` never calls an uninitialized SDK client;
- every synchronous Reown call used for pairing, session approval/rejection,
  request response, lookup, or disconnect reports a recoverable SDK error
  instead of escaping the UI coroutine;
- synchronous Reown runtime failures are reported without terminating app
  startup, while cancellation and fatal virtual-machine/linkage errors still
  propagate; and
- an unavailable WalletKit session store produces an empty connections list
  instead of crashing the Connections screen.

Focused tests cover unavailable core and wallet clients, partial-registration
retry, concurrent registration, object loading, session fallback and deletion
races, non-readiness runtime failures, synchronous SDK action/startup failure,
cancellation, and fatal-error propagation. Pull-request IAS builds
intentionally receive no WalletConnect secret. The trusted
protected-`develop` dispatch fails closed unless its exact bundle step receives
the non-logged 32-hex project ID. Final acceptance still requires an in-place
release-like device install, a valid `wc:` pairing scan, and at least five
minutes of post-navigation process and crash-log observation.

## Candidate scope

### Wallet and database preservation

- The Room database accepts only the complete adjacent upgrade path from
  versions 9 through 77. Missing, duplicate, non-adjacent, or out-of-range
  migration edges fail before Room opens the wallet; there is no destructive
  migration fallback.
- Historical schemas, SQL shapes, row counts, foreign keys, cursors, and wallet
  secret/public-identity bindings are validated with explicit bounds. Invalid,
  oversized, ambiguous, or attacker-expanded state stops startup without a
  partial migration.
- Legacy wallet rows are preserved in an explicit recovery ledger where they
  cannot be represented safely in the current schema. Unreadable or
  identity-mismatched ciphertext is retained under deterministic quarantine
  keys instead of being discarded.
- Startup attests the Android Keystore-backed master key before PIN, signing,
  export, or the main wallet UI becomes available. Retryable storage failure,
  permanent key loss, database failure, and process-restart-required state are
  handled separately and fail closed.
- Account create/add-EVM/delete operations and TON Connect mutations use
  durable cross-store journals. Startup replays or reconciles those journals,
  then inventories orphaned active/quarantined secret namespaces before the
  wallet can become ready.
- One process-owned startup session serializes the database gate across
  rotation, launcher intents, and deep links. A ready activity retains the
  newest intent, and a secure-storage health transition invalidates the
  session and redirects through a fresh process startup.

### Platform and release hardening

- Android builds use compileSdk 36, exact AGP 8.10.1 / R8 8.10.24, Gradle 9.0,
  JDK 21, NDK r28 native artifacts, and Reown BOM 1.6.9.
- Release dependency resolution is locked and verification is strict for the
  wrapper, root buildscript classpath, production graph, and pinned
  `fearless-utils` source/patch.
- The signed AAB must contain the exact package/version/source identity, exact
  16-library native inventory, explicit cleartext denial, and no broad media or
  legacy external-storage permissions.
- MoonPay remains disabled and absent from the buy-provider registry. Do not
  restore its former client-side signing secret; re-enable it only after
  backend signing or a supported public mobile flow exists.

## Signed artifact workflow

Do not use a local release task, debug signing fallback, Gradle Play publisher,
or locally produced AAB as the release artifact.

1. Merge the exact reviewed candidate through the protected branch flow and
   wait for exact-head CI to pass on `master`.
2. Replace the fail-closed signer-fingerprint sentinel only with the reviewed
   OpenSSH Ed25519 fingerprint, and configure the matching public key and the
   two protected environments as described below.
3. Create and push the annotated SSH-signed tag from the exact `master` commit:

   ```sh
   git -c gpg.format=ssh \
     -c user.signingkey=/secure/path/release_ed25519 \
     tag -s 'v4.2.0+android.230' \
     -m 'Fearless Android 4.2.0 build 230'
   git push origin 'v4.2.0+android.230'
   ```

4. Dispatch `Android Signed Release Artifact` for that tag. Its three-stage
   trust split is mandatory:

   - credential-free `release-controls` validates the immutable signed tag,
     exact `master` source and prior CI, protected-environment governance,
     source tree, and all adversarial controls;
   - protected `release-build` restores only production Firebase and creates
     the exact CI-only/source-bound unsigned `:app:bundleRelease`. It attests
     and transfers exactly four files: AAB, checksum, provenance, and bounded
     verified Gradle/R8 build log; and
   - separately protected `release-signing` revalidates those four files on a
     fresh runner before restoring the upload key. The standalone signer
     preserves every non-signature ZIP entry, verifies the pinned upload
     certificate, and emits exactly three final files: signed AAB, checksum,
     and provenance, each attested.
5. An authorized operator downloads `fearless-android-signed-<tag>` and verifies
   all three files, attestations, checksum, provenance, embedded source commit,
   identity, permissions, native inventory, and upload-certificate fingerprint
   before opening Play Console.

CI must never receive a Play service-account credential and must never mutate
a Play track.

## Monitoring and stop criteria

- Monitor Play pre-launch results, crash-free users/sessions, ANRs, startup
  recovery diagnostics, wallet creation/import/export, signing, transfers,
  Reown sessions, and TON Connect reconciliation.
- Stop the testing release for any P0/P1 regression, any wallet/account loss or
  silent reset, a startup crash loop, an unrecoverable migration/journal
  mismatch, or a material crash/ANR regression.
- Preserve affected app data and encrypted recovery state for diagnosis. Do
  not instruct testers to clear app data or reinstall until recovery/export
  options have been assessed.
- Production promotion is a separate reviewed decision after Open Testing exit
  criteria are met; it is not part of this candidate procedure.
