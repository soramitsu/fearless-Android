# Subject-bound Google Drive backup candidate

The disabled Android passkey backup adapter now identifies a selected Drive account by Google's stable OIDC `sub`, matching iOS's Google account subject. Email remains display/selection information and the original encrypted envelope's authenticated metadata. It is not an owner identifier and is never rewritten inside an existing FPBKAEAD envelope after a Google email rename.

The existing pinned `GoogleAuthUtil` token fetcher requests `oauth2:https://www.googleapis.com/auth/drive.appdata openid email`. The additional identity scopes require user consent; neither full Drive access nor profile scope is requested. The adapter sends that exact bearer token to the fixed `https://openidconnect.googleapis.com/v1/userinfo` HTTPS endpoint. It requires a nonempty valid `sub`, a valid email and literal boolean `email_verified: true`. Initial identity must match the selected account's email. Subsequent identity must match the pinned subject even if the current email changes. Selection changes during asynchronous token/identity work and concurrent attempts to repin the provider are rejected.

The default identity transport has no cache, interceptors, redirects or automatic retry, uses a 30-second call deadline and bounds the response to 8 KiB. Parsing rejects duplicate fields, invalid UTF-8, trailing JSON, missing/wrong-typed claims, unverified email and oversized or structurally unexpected responses. Errors and descriptions do not include response bodies or bearer tokens. The access-token backing field is excluded from Gson serialization.

`GoogleDrivePasskeyBackupDriveClient` requires an explicit expected subject, obtained from a successfully verified account selection. Before every list page, download, upload or delete request, it obtains a verified token and compares its subject with that immutable selection. A token for another subject cannot be substituted even if the email is unchanged. Each appData namespace is authorized by Google for that bearer, so a historical file's `accountName` cannot override the selected account. Wallet identity, schema, duplicate-file, pagination and bounded legacy-property checks remain in place. Returned/uploaded records retain their original five metadata properties and encrypted bytes; no new storage format is introduced.

The provider's subject pin is scoped to its instance, not a new durable owner record. Changing accounts requires an explicit new selection/provider and a new Drive client bound to the verified subject. Existing selected clients cannot silently follow that account change. Cross-platform recovery still requires both native OAuth clients to belong to the same reviewed Google Cloud appData project.

Google's [OIDC reference](https://developers.google.com/identity/openid-connect/reference) defines `sub` as stable across email changes and documents the UserInfo endpoint. [Android authorization guidance](https://developer.android.com/identity/authorization#get-user-information) explains obtaining account information using the same authorized bearer with identity scopes. The pinned [GoogleAuthUtil API](https://developers.google.com/android/reference/com/google/android/gms/auth/GoogleAuthUtil) supports space-separated OAuth scopes and recoverable consent; it is deprecated in favor of AuthorizationClient. This bounded patch retains the existing token fetcher and propagates its consent requirement. Migrating the consent/UI path to AuthorizationClient remains separate work.

Recovery remains disabled. Google identity/Drive possession does not recover, replace or authorize an existing Fearless owner; owner/grant authority, native PRF/provider qualification, enrollment and final-credential removal, key rotation, immutable generation/rollback handling, OAuth configuration/consent UI and real bidirectional replacement-device acceptance remain required. Unit and loopback tests use synthetic identities/tokens only, and are not live Google or shipping-artifact evidence.
