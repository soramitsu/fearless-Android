# WP-9 send correctness

This lane continues from WP-5/6/7 `9718a1d5ee185c6781878c2f2dd7c3c23336b1c0`. The binding safe-upgrade decisions keep BTC/SOL sending enabled by default with sticky remote vetoes. Protocol qualification and private-chain execution are separate gates; this document does not authorize public-network transfers.

## Foundation

- Bitcoin address balances accept a signed outgoing mempool delta while rejecting negative raw counts/sums, negative confirmed/total balances and overflow. This permits a fresh pending-spend balance to replace stale cached funds.
- Estimated fees use a configurable relay floor (minimum/default 1 sat/vB) and the existing 10,000 sat/vB ceiling. Explicit selector/planner rates below the floor fail. The selector absorbs only a bounded uneconomical change remainder and exposes an exact all-input, one-output sweep primitive.
- Route validation enforces BIP173 checksum, case, network, witness version and payload length for the currently supported P2WPKH output type. Unsupported address types fail before signing. The recovery checkpoint adds recipient guidance and native Max/fee UI.
- Signed Bitcoin inputs use sequence `0xfffffffd`, including the BIP143 hash. The independent public BIP39 transaction generated by bitcoinjs-lib 6.1.7 is signature-verified before recording its expected txid/bytes. No fee-bump UI is claimed.
- The Esplora client uses Blockstream and mempool.space with sticky success and bounded cooldowns on transport errors, HTTP 408/429/5xx. An explicit endpoint outside the exact selected-network public pool stays isolated, including emulator hosts, LAN/private TLS endpoints, and a public URL for the other network. Broadcast fallback resubmits identical bytes. The reviewed-send and recovery checkpoints add the required durable ambiguous-broadcast journal.
- Solana RPC supports explicitly scoped same-cluster providers, a public mainnet fallback, atomic request IDs, and preserved provider query strings. Arbitrary devnet/private overrides never silently fall back to mainnet. Node-lag RPC errors retry; deterministic simulation failures do not.
- Solana ATA derivation previously tested `Ed25519.validatePublicKeyFull`, which checks signing-key subgroup validity. Solana instead checks whether a compressed Edwards point decompresses. The old implementation disagreed with an independent web3.js matrix for 14 of 32 owners. `SolanaPdaCurve` now follows Dalek's field reduction and square-root existence contract, including small-order/sign/noncanonical cases, without changing signature verification.

## RPC balances and account preflight

The production Solana balance source now reads `getBalance` and both standard SPL/Token-2022 `getTokenAccountsByOwner` inventories from the selected node. It no longer needs indexer service-info or metadata. Exact token owner/program/mint/decimal and full unsigned-64-bit balances survive normalization; partial, malformed, duplicated or inconsistent inventory responses leave prior balances intact. Frozen token balances remain visible and are excluded from transferable amounts. The older indexer adapter is retained for historical contract tests; DI binds the RPC implementation.

RPC now supports bounded account-data slices, block height, signature history and recent priority-fee samples. The separate account preflight checks signing-capable wallet keys, System Program ownership, SPL mint initialization/decimals, and exact mint/wallet/program/state in source and destination token accounts. Native and token rent checks reject insufficient funds and non-exempt remainders before signing. The reviewed-send checkpoint integrates these guards into immutable send review and broadcast. Token-account addresses are not silently treated as wallet recipients.

The SPL byte layouts follow the [official token interface](https://github.com/solana-program/token/blob/main/interface/src/state.rs); account absence and owner/data fields follow [`getAccountInfo`](https://solana.com/docs/rpc/http/getaccountinfo). Signing-key checks intentionally remain distinct from the PDA decompression contract.

## Reviewed production sends and durable pending guard

The Bitcoin service now scans the same receive/change branches used for balance display, proves the root matches the selected wallet before scanning, spends every needed confirmed source with its path, and derives an unused owned internal change address. Total and transferable balances are separate; pending amounts cannot inflate Max. A review holds exact inputs, outputs and fee. Send rechecks those inputs and signs the same plan, without fetching another fee or selecting new coins. Max uses the one-output sweep.

The Solana service now uses the RPC-only planner for native SOL and standard SPL. Quotes contain complete legacy message bytes, bounded compute-unit priority policy, exact network fee, separate ATA creation rent, source allocations across token accounts, and blockhash expiry. Preflight checks wallet/mint/program/ownership/rent and supports full u64 SPL amounts. Send rechecks the exact quote, signs it, simulates with signature checking and without blockhash replacement, then retains those signed bytes before submission. The three native/SPL messages match pinned official web3.js 1.98.4 and SPL Token 0.4.14 fixtures, including two-source full-u64 transfers and both ATA states.

`WalletSendJournal` durably saves public signed bytes before network I/O, verifies exact read-back, and rejects corrupt or uncertain storage. A wallet/network mutex spans checking, signing, retention and submission. An ambiguous pending payment blocks a different intent. Retry uses only the retained bytes; confirmed/failed chain evidence may settle it, while an absent signature or blockhash expiry alone does not prove a previous payment never landed. A restart may retry existing bytes but cannot silently reconstruct an uncached review.

Confirmation uses one cached quote ID and the displayed fee. It no longer recalculates on the Send tap or adds the unrelated 0.01 fee correction to BTC/SOL. Native Max, BTC sat/vB and separate Solana account creation are connected to that review. The central Room selection transaction increments a process-local revision before and after selection; A→B→A therefore invalidates old work even if observation conflates B. Canceled quote requests cannot publish late results.

The subsequent recovery checkpoint adds dedicated persistent pending-payment controls, explorer/history fallback and complete eight-locale review/error guidance. The subsequent checkpoints below independently qualify Setup/Confirm native display and private-chain execution. Public networks have not received transactions from this work.

## Shared Solana contract alignment

The Solana send behaviour now matches the contract shared with iOS and the browser extension;
`docs/solana-send.md` lists each rule with its tests. Changes to the statements above:

- Endpoints are ordered as an optional `https` build provider (`FL_ANDROID_SOLANA_RPC_URL`,
  mainnet only), the selected node, `api.mainnet-beta.solana.com`, `solana-rpc.publicnode.com`,
  `public.rpc.solanavibestation.com` (requests spaced 700 ms for its rate limit),
  then other configured nodes. A user-selected mainnet node is followed by the public nodes;
  devnet and private clusters stay isolated. Balance loads use the same list.
- Any HTTP 4xx except 408/429 moves a read or a broadcast to the next endpoint. A broadcast's
  JSON-RPC error is final only when a node gives it before relaying (-32002, -32003, -32600,
  -32602, -32700), hands over for -32601, -32004, -32005, -32014 and -32016, and otherwise
  means the bytes may have been relayed: later endpoints only relay them.
- A failed token-account read keeps SOL current and leaves token rows at their last amounts.
- Token-2022 sends are refused with a dedicated message before the quote is built.
- An existing plain System account at an off-curve address may receive SOL.
- Broadcast failures are classified as not sent, refused or ambiguous. A first submission that
  is not sent or refused is released immediately. Endpoints are asked for the outcome at once,
  15 seconds each. A pending payment is released only when every endpoint that answers proves
  expiry on its own: finalized progress from one `getEpochInfo` past the blockhash's last valid
  height, then a signature lookup from a slot at least that recent with no trace. Any confirmed
  status settles it; any unconfirmed trace, lagging lookup or endpoint not yet past the height
  keeps it pending, except that with three or more answers an endpoint more than 1,000 finalized
  slots behind the lower median abstains (its trace still counts).
- A release ends the call that found it, so the user confirms again before a new payment is
  signed. The history row closes before the record is removed: as failed only when at least two
  distinct hosts each proved the expiry within six hours of signing (spellings of one host count
  once), otherwise as Unknown with a message to check the balance and explorer (the recovery
  dialog keeps its explorer button).
- The send screen validates Solana and Bitcoin recipients in their own formats and leaves
  balance, fee and rent rules to the quote.
- Without history-service data, the history list says so under the explorer link (Solscan).
